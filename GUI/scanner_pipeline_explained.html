The Scanner Pipeline: Detection → Learning → Action

What the 20 questions learn, how symptoms are found and labeled, and exactly what happens to 10,000 files in a folder.

Part 1: The 20 Questions — What Each One Learns

The scanner asks 20 questions about every folder it enters. Each question produces a specific, actionable fact. Nothing is vague. Every answer feeds the next step.

Q1 — What file types are here?
Count unique extensions per directory.
Learns: Is this a focused project folder or a dumping ground? >8 types = extension swamp (S01).
Q2 — Are there duplicate versions?
Regex for _v1, _v2, _FINAL, _copy, (1), (2).
Learns: Which files are version sprawl (S02) and which is the real current one.
Q3 — How deep is the tree?
Walk depth. Flag paths >5 levels with <3 files at leaf.
Learns: Depth explosion (S03). The path exists but nothing useful is down there.
Q4 — How wide is each directory?
Count files per dir. Flag >200.
Learns: Flat overload (S04). This is the "10,000 files" problem — scroll paralysis.
Q5 — Are there orphan sidecars?
Find .chi, .fmeta, .srt, .meta.json without a parent file.
Learns: Dead metadata (S05). The parent was moved or deleted.
Q6 — Are names colliding?
Case-insensitive match within same directory.
Learns: Naming collision (S06). report.md vs Report.md vs REPORT.md — which is canonical?
Q7 — Is one project scattered?
Detect shared keywords/project markers across distant directories.
Learns: Project scatter (S07). Theophysics files in D:\, O:\, Z:\, and Downloads.
Q8 — Are there broken links?
Parse markdown/HTML links, check if targets exist.
Learns: Phantom references (S08). [[deleted_page]] in Obsidian.
Q9 — Are files duplicated?
Group by size, then MD5 hash identical files.
Learns: Duplicate clusters (C01). Same PDF in 3 folders — which is the keeper?
Q10 — Same content, different formats?
Same stem as .md + .html + .pdf + .docx.
Learns: Format redundancy (C02). Edits only get applied to one format.
Q11 — Are there abandoned drafts?
Regex for draft/wip/old/temp in name + age >30 days.
Learns: Draft graveyard (C03). Good ideas buried in files nobody opens.
Q12 — Are doc types mixed randomly?
3+ doc types (.pdf/.docx/.xlsx) in one dir with no grouping.
Learns: Document chaos (C04). Budget spreadsheet next to sermon notes next to code.
Q13 — Are media files auto-named?
Match IMG_, DSC_, Screenshot_, VID_ patterns.
Learns: Media dump (C05). 500 photos named IMG_4587.jpg.
Q14 — Are there unknown file types?
Extension not in the known-extension list.
Learns: Unknown blobs (C06). Could be anything. Quarantine first.
Q15 — How old are the files?
Compare file ages to folder activity. Stale files in active dirs.
Learns: Time bombs (T01) and abandoned workspaces (T04). Forgotten files in busy folders.
Q16 — Is this a program root?
Check for .git, package.json, pyproject.toml, venv.
Learns: Program root danger (I01). NEVER auto-move. Mark as PROTECTED.
Q17 — Are credentials exposed?
Find .env files, scan for api_key=, sk-, AKIA patterns.
Learns: Config leak (I03). CRITICAL. Alert immediately.
Q18 — Are sync conflicts present?
Match "sync-conflict", "conflicted copy" in filenames.
Learns: Sync ghosts (I04). OneDrive/Syncthing created duplicates.
Q19 — Are research files tagged?
Check for .chi sidecar or chi_catalog entry for canonical files.
Learns: Untagged canonical (R01). Important work that the system can't classify.
Q20 — What's the chi-variable signature?
Run the semantic scorer: 250 signal words → 10 variable scores → coordinate hash.
Learns: THE IDENTITY OF EVERY FILE. G=0.8, M=0.2, E=0.9... → hash GEC-3K5A-3F. This is the semantic address.

Part 3: How Symptoms Are Labeled

Every symptom the scanner finds gets a structured label. This is the language the system speaks.

Symptom Label Structure 
{
  "symptom_id": "S04",                    // Which symptom
  "category":   "Structural",             // Which family
  "severity":   "medium",                 // low / medium / high / critical
  "name":       "Flat overload",          // Human-readable name
  "count":      1,                        // How many instances found
  "auto_fixable": false,                  // Can the system fix it alone?
  "priority_code": 40003,                 // From the numbering schema
  "affected_paths": ["D:\\Downloads"],     // Where
  "recommended_action": "classify + split by domain/date"
}

What Each Severity Means Operationally

  • LOW Cosmetic. No data loss risk. Auto-fixable in most cases. Empty folders, orphan sidecars, old drafts. The system CAN fix these without asking. Review monthly in batch.
  • MEDIUM Functional impact. Potential confusion. Files become hard to find. Extension swamps, duplicates, document chaos. The system PROPOSES fixes but WAITS for approval. Review weekly.
  • HIGH Structural risk. Potential data loss or broken references. Naming collisions, project scatter, sync conflicts. Requires CAREFUL PLANNING. Address within 48 hours.
  • CRITICAL Security or integrity risk. Exposed credentials, program roots at risk. The system NEVER auto-fixes these. ALERTS IMMEDIATELY via ntfy. Human acts within minutes.

Part 4: What Happens to Files — Every Action Explained

File Actions

📝
RENAME

Old name → new name. The old name is logged in the ledger. The .chi sidecar (if any) is updated. All internal links pointing to the old name are flagged for repair. Extensions are NEVER changed during rename. The system suggests 3 candidates ranked by confidence.

IMG_4587.jpg → 2026-03-15_church-event-group-photo.jpg

📦
MOVE

Source folder → destination folder. The ledger records both paths. If the file had a .chi sidecar, it moves too. If other files referenced this one, they're flagged for link repair. Moves are REVERSIBLE via the ledger — the system can always undo.

D:\Downloads\paper.pdf → O:\_Theophysics_v5\papers\paper.pdf

🗄️
ARCHIVE

Move to .archive/ inside the same parent directory. The file is still on disk, still recoverable, but out of the active workspace. Archives are timestamped: .archive/2026-07-03/file.pdf. This is the default for duplicates, old drafts, and stale pipeline outputs.

🗑️
DELETE (soft)

Move to .trash/ with timestamp. NEVER permanent deletion in V1. ALWAYS requires human approval regardless of count. The ledger records the original path so recovery is one command. Trash is reviewed monthly — only then is it truly gone.

📋
CLASSIFY

Run the semantic scorer → get chi-variable scores → compute coordinate hash → write to the .chi sidecar file OR store in the hub database (depending on folder policy). Classification does NOT move or rename anything. It's read-only intelligence gathering.

sermon_notes.md → chi signature: GFC-2K5A-4A (Grace=0.9, Faith=0.8, Christological=0.7)

🔒
PROTECT

Mark the folder/file as NEVER-TOUCH. Program roots (.git, node_modules, venv), canonical archives, and anything the human explicitly flags. The system will scan and classify but REFUSE to rename, move, archive, or delete anything inside a protected zone.

📎
WRITE SIDECAR

Create a .chi or .meta.json file next to the original. Contains: chi-variable scores, coordinate hash, meta classification (CONTEXT/DOMAIN/FUNCTION/STATE), source AI, confidence, and timestamp. The sidecar is invisible to humans but readable by any AI or script.

Part 5: The 10,000-File Folder — What Actually Happens

You have a folder with 10,000 files. Here is the exact sequence of what happens when the scanner hits it.

Phase 1: Discovery (30 seconds)

Walk the directory. Count: 10,247 files, 3 subdirectories, 847 unique filenames, 23 file extensions.

Q4 fires immediately: S04 FLAT OVERLOAD — 10,247 files in one directory.

Q1 fires: S01 EXTENSION SWAMP — 23 different file types mixed together.

The folder is already diagnosed as GRADE F before the scanner even reads file contents.

Phase 2: Sampling (60 seconds)

The scanner does NOT read all 10,000 files. It takes a stratified sample:

  • First 50 files alphabetically
  • Last 50 files alphabetically
  • 50 random files from the middle
  • ALL files with sizes in the top 5% (the big ones matter)
  • ALL files with dangerous extensions (.env, .key, .pem)

Sample size: ~200 files. Enough to characterize the population without reading 10,000.

Phase 3: Classification (90 seconds on the sample)

Each sampled file gets classified through 4 layers:

Layer 1 — Physical: extension (.pdf), size (2.4 MB), date (2025-11-03), path depth (0).

Layer 2 — Semantic: Run the 250-word scorer on the first 5KB of text. Produces chi-variable scores. Example: a file about thermodynamics scores E=0.9, S=0.8, K=0.3 → hash ES-4K5A-3A.

Layer 3 — Meta: Auto-derived from Layer 2 scores. BUSINESS.LEARNING.DOCUMENT.ACTIVE

Layer 4 — Relational: What project does this belong to? What source AI created it? Who owns it?

Phase 4: Clustering — HOW THE FOLDER GETS NAMED

This is the answer to "how do we name a folder with 10,000 files?"

You don't name the FOLDER. You name the CLUSTERS inside it. The folder becomes multiple folders, each named by what's actually in it.

The clustering algorithm:

1. Group all 10,247 files by their dominant chi-variable (the highest-scoring variable from Layer 2).

2. Within each group, sub-group by file extension.

3. Within each sub-group, sub-group by date range (same month = same bucket).

4. Name each cluster using the pattern: {dominant_variable}_{domain}_{date_range}

5. If a cluster has fewer than 5 files, merge it into the nearest neighbor.

How Folder Names Are Generated

Naming rules (deterministic, no AI needed):
  • Prefix: dominant chi-variable mapped to a human word: G=grace, M=ethics, E=research, S=code, T=history, K=community, R=recovery, Q=media, F=faith, C=theology
  • Middle: meta-domain from Layer 3: physics, theology, personal, finance, software, media
  • Suffix: date range in the cluster: 2025Q4, 2026Q1, 2026-06, ongoing
  • Format: {category}_{domain}_{date_range} → all lowercase, underscores, no spaces
  • Special prefixes: _unknown, _duplicates, _protected (underscore = system-managed)

If Ollama is available, the system can generate a more natural name by summarizing the cluster's content. But the deterministic name is always the fallback and always works.

Part 6: What Gets Stored After Every Scan

Per file (in the hub database):
  • file_id, current_path, original_path
  • sha256 hash + quick_hash (first 8KB)
  • chi-variable scores: vec_G through vec_C (10 floats)
  • coordinate hash: GKC-3K5A-3F
  • meta classification: CONTEXT.DOMAIN.FUNCTION.STATE
  • symptom IDs affecting this file
  • proposed actions (rename/move/archive) — NOT executed yet
Per folder (in the hub database):
  • folder_id, path, role (intake_hub / research / program_root)
  • file_count, dir_count, total_size
  • health grade (A-F), score (0-100)
  • symptom list with counts
  • dominant chi-variables for the folder population
  • proposed subfolder structure (the clustering result)
  • last_scanned timestamp
  • trend: score_delta vs previous scan
In shared memory (accessible to all AIs):
  • scan_Downloads_20260703 → "Grade D (38/100), 14 symptoms, 340 duplicate clusters"
  • folder_role_Downloads → "intake_hub"
  • chi_dominant_Downloads → "Q (media), E (research), S (code)"
In the scan report (HTML file):
  • Visual grade circle
  • Category breakdown bars
  • Prioritized work order table with effort estimates
  • Symptom detail cards with affected paths
  • Delta comparison vs previous scan
  • Proposed folder structure (the clustering diagram)

Part 7: The Learning Loop

What the system learns from YOUR behavior:
  • Accept a rename → the naming pattern is reinforced for that folder profile. After 50 accepts, the system predicts your preferences with >70% accuracy.
  • Reject a rename → the pattern is suppressed. The system asks: was it the prefix? the date format? the domain word? It learns which part was wrong.
  • Move a file manually → the system records: "David moved .lean files to Z:\__ CODEX CLAUDE Production." Next time a .lean file appears in Downloads, the system suggests that destination.
  • Ignore a symptom → the system doesn't repeat the alert next scan. But the symptom stays in the report. Ignoring is different from fixing.
  • Fix a symptom → the score goes up next scan. The system compares before/after and learns which fixes produce the most score improvement.

Rule: Learning is SCOPED. What David does in Downloads doesn't affect what happens in O:\_Theophysics_v5. Each folder profile has its own preference history. A local correction never becomes a global rule without explicit approval.
