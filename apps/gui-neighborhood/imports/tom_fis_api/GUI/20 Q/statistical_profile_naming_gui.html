How we derive the user's fingerprint faster than anyone, 3 snap-switch naming conventions, and exactly how many GUIs you need.

Part 1: The Statistical Profile

The statistical profile is a fingerprint of how this specific user organizes files. It's derived automatically from observed behavior — no questions asked, no preferences configured. Here's what it contains and how fast each piece can be computed.

The Profile Object

UserProfile {
  // Identity
  user_id:              string
  observations_count:   int
  profile_version:      int
  first_observed:       datetime
  last_updated:         datetime
  trust_level:          0-4

  // SEPARATOR PREFERENCE (derived after ~5 actions)
  separator:            "_" | "-" | "." | " " | "camelCase"
  separator_confidence: 0.0 - 1.0
  // How derived: count separators in the last 20 renamed files.
  //   underscore_count: 14  → separator = "_", confidence = 0.70

  // CASE PREFERENCE (derived after ~5 actions)  
  case_style:           "lowercase" | "Title_Case" | "UPPER" | "mixed"
  case_confidence:      0.0 - 1.0
  // How derived: check first char and overall case of last 20 renames.

  // DATE PREFERENCE (derived after ~8 actions)
  uses_dates:           boolean
  date_position:        "prefix" | "suffix" | "none"
  date_format:          "YYYY-MM-DD" | "YYYY_MM_DD" | "YYYYMMDD" | "MM-DD-YYYY"
  date_confidence:      0.0 - 1.0
  // How derived: regex scan for date patterns in renamed files.
  //   8 of 12 renames include dates → uses_dates = true
  //   6 of 8 have date at start → date_position = "prefix"
  //   5 of 6 use YYYY_MM_DD → date_format = "YYYY_MM_DD"

  // DESTINATION MAP (derived after ~15 actions per type)
  destination_map: {
    ".pdf":  { primary: "D:/Finance/", secondary: "D:/Research/", confidence: 0.78 },
    ".py":   { primary: "D:/GitHub/scripts/", confidence: 0.92 },
    ".lean": { primary: "Z:/CODEX/", confidence: 0.95 },
    ".png":  { primary: "D:/Screenshots/", confidence: 0.65 },
    ".xlsx": { primary: "D:/Finance/", confidence: 0.70 },
    ".md":   { primary: "O:/_Theophysics/", secondary: "Z:/vault/", confidence: 0.55 },
  }
  // How derived: frequency counting with recency decay per extension.
  // Split destinations (confidence < 0.6) mean the user sends this
  // type to different places depending on content — needs chi-signal.

  // TEMPORAL PATTERN (derived after ~30 actions)
  active_hours:         [9, 10, 11, 14, 15, 22, 23, 0, 1]  // hours of activity
  cleanup_times:        ["monday_morning", "friday_evening"]
  burst_pattern:        "downloads_first_then_organize"
  // How derived: bucket actions by hour and day-of-week.
  //   Cluster detection: if >60% of organize actions happen
  //   Monday 8-10am → that's a cleanup ritual.

  // FOLDER DEPTH PREFERENCE (derived after ~20 actions)
  preferred_depth:      2-3      // how deep do they nest?
  max_depth_tolerance:  5        // beyond this they flatten
  prefers_flat:         false    // true if they rarely go past depth 1
  // How derived: measure destination folder depths.

  // NAMING LENGTH (derived after ~10 renames)
  avg_name_length:      24       // characters (stem only)
  name_length_range:    [8, 45]  // min-max
  uses_abbreviations:   true     // "inv" vs "invoice"
  // How derived: stats on renamed file stems.

  // CO-OCCURRENCE BUNDLES (derived after ~40 actions)
  bundles: [
    { extensions: [".py", ".json", ".yml"], label: "code_project" },
    { extensions: [".pdf", ".xlsx"],        label: "financial_docs" },
    { extensions: [".md", ".excalidraw"],   label: "research_notes" },
  ]
  // How derived: association rule mining on files moved within 60s.

  // VOCABULARY (derived after ~20 renames)
  common_prefixes:      ["inv", "screenshot", "draft", "meeting"]
  common_suffixes:      ["final", "v2", "backup", "cleaned"]
  domain_words:         ["theophysics", "finance", "lean", "sermon"]
  // How derived: tokenize all renamed file stems, count frequency.

  // PREDICTION ACCURACY HISTORY
  accuracy_history: [
    { week: "2026-W27", predictions: 45, correct: 31, rate: 0.689 },
    { week: "2026-W28", predictions: 52, correct: 41, rate: 0.788 },
  ]
  permanent_rules_count: 7
}

Derivation Speed — The Edge

Here's where the competitive advantage comes from. The profile doesn't need 500 actions to be useful. Different parts converge at different speeds:

ACTIONS    WHAT YOU KNOW                    ACCURACY IMPACT
────────   ──────────────────────────────   ─────────────────
    3       separator preference             +5% (stop guessing _ vs -)
    5       case preference                  +3% (lowercase vs Title)
    8       date format preference           +7% (know whether to add dates)
   10       naming length preference         +3%
   15       primary destination per type     +20% (biggest single jump)
   20       folder depth preference          +5%
   30       temporal pattern                 +5%
   40       co-occurrence bundles            +5%
   50       vocabulary / domain words        +3%
  100       split-destination disambiguation +8% (chi-signal resolves ambiguity)
  200       preference refinement            +5%

CUMULATIVE:
  After  5 actions:  ~8%  better than random
  After 15 actions:  ~28% better than random (destination map kicks in)
  After 30 actions:  ~41% better than random
  After 50 actions:  ~49% better than random → roughly 60% absolute accuracy
  After 100 actions: ~57% better → roughly 70% absolute accuracy
  After 200 actions: ~62% better → roughly 80% absolute accuracy

The trick is: separator, case, and date preferences converge in the first 5-8 actions. That means the system can already suggest well-formatted names before it even knows WHERE the file should go. The user sees "oh, it got the naming right" immediately, which builds trust for the destination prediction that takes longer to converge.

The edge over competitors: Most file organizers wait until they have a complete picture before doing anything. We don't. We start showing value after 3 actions — just the separator preference is enough to format names correctly. Each new piece of the profile adds visible improvement. The user watches the system get smarter in real time. That's the trust ramp.

How To Derive It Faster — The Cheat Codes

Cheat 1: Scan existing files before observing any actions.

The user's file system already contains hundreds of naming decisions. Before the user does anything, scan 200 files in their Documents, Desktop, and Downloads folders. Extract separator, case, date format, and depth preferences from what already exists. This gives you a warm start — the profile is 60% complete before the user takes a single action.

Cheat 2: Run spell correction in the background.

While the user is working, pre-compute corrected names for every file in the active directory. Use a simple word list (not an LLM). When the user goes to rename, the corrected name is already ready — zero wait. Cache it in SQLite. The user perceives instant response.

Cheat 3: Pre-compute the destination for every file in Downloads.

Don't wait for the user to pick a file. The moment a file appears in Downloads, run the 5-signal prediction engine on it in the background. Store the result. When the user clicks on it, the prediction is already waiting. Speed is perceived as intelligence.

Cheat 4: Capitalize on the first correction.

When the user overrides a prediction, don't just learn from that one file. Ask: "Would you like me to apply this to all similar files?" One correction + one "yes" = 50 files organized. That's the highest-leverage moment in the entire system. One action → 50 results.

Part 2: The Three Naming Schemas

Three naming conventions. The user picks one. Their entire file system reformats. Snap.

Schema A: Clean Professional
invoice_march_2026.pdf
project_proposal_acme_v2.docx
meeting_notes_2026_07_03.md
screenshot_pof_hub_architecture.png
RULES:
  separator:     underscore (_)
  case:          all lowercase
  date:          suffix, YYYY_MM_DD
  structure:     {type}_{description}_{date}.{ext}
  max_length:    60 chars
  spell_correct: yes
  strip:         IMG_, DSC_, Screenshot_, (1), (2), _FINAL, _copy
  abbreviations: no (spell out fully)
Best for: professional work, shared drives, team environments. Everything is searchable, sortable by name, and unambiguous.
Schema B: Date-First Archive
2026-07-03_invoice_march.pdf
2026-07-01_project_proposal_acme.docx
2026-07-03_meeting_notes.md
2026-07-03_pof_hub_architecture.png
RULES:
  separator:     hyphen (-)  
  case:          all lowercase
  date:          prefix, YYYY-MM-DD
  structure:     {YYYY-MM-DD}_{description}.{ext}
  max_length:    60 chars
  spell_correct: yes
  strip:         same as Schema A
  abbreviations: no
Best for: chronological work, journals, research logs, anything where "when" matters more than "what." Files sort chronologically in any file explorer automatically.
Schema C: Smart Compact
inv.march.2026.pdf
prop.acme.v2.docx
notes.mtg.0703.md
ss.pof-hub.png
RULES:
  separator:     period (.)
  case:          all lowercase
  date:          suffix, MMDD (short)
  structure:     {abbrev}.{description}.{date}.{ext}
  max_length:    35 chars
  spell_correct: yes (but abbreviate common words)
  strip:         same as Schema A
  abbreviations: YES — built-in abbreviation map:
    invoice→inv  screenshot→ss  meeting→mtg
    project→proj  proposal→prop  document→doc
    notes→notes  report→rpt  presentation→pres
Best for: power users, deep folder trees, terminal users, anyone who types paths. Short, dense, still readable. Solves the N04 path-length problem by design.

The Snap-Switch Mechanic

Naming Schema — Settings

Choose your naming convention. All future suggestions and "Always do this" rules will follow this schema. Existing files can be batch-renamed to match.

A: Clean Professional ✓ B: Date-First Archive C: Smart Compact

Switching schemas doesn't rename existing files automatically. It changes all future predictions and suggestions. To apply the new schema to existing files, use "Batch rename to schema" in the review queue.

What Happens Behind the Scenes on Schema Switch

When the user snaps from Schema A to Schema B:

1. All cached name suggestions in SQLite are invalidated and recomputed in the background

2. The prediction engine's naming pattern signal switches to the new schema's rules

3. A batch job is queued: "Preview what 500 files would look like in Schema B" — but NOT executed

4. The preview appears in the review queue: "47 files in Downloads would change. 203 in Documents. Want to see them?"

5. The user can approve all, approve per-folder, or just let it apply to new files only

The snap is the switch. The application is incremental and reviewable.

Part 3: The Name Normalization Pipeline

What runs in the background on every file, caching standardized names before the user ever asks.

RAW FILENAME
    │
    ▼
┌────────────────────────┐
│ 1. STRIP JUNK          │  Remove: IMG_, DSC_, Screenshot_, (1), (2),
│                        │  _copy, _FINAL, _v1, _v2, _backup, -Copy
│                        │  "IMG_4587.jpg" → "4587.jpg"
└──────────┬─────────────┘
           ▼
┌────────────────────────┐
│ 2. SEPARATOR NORMALIZE │  Replace all separators with the schema's separator.
│                        │  Collapse multiples. Trim edges.
│                        │  "my--file   name_here" → "my_file_name_here"
└──────────┬─────────────┘
           ▼
┌────────────────────────┐
│ 3. CASE NORMALIZE      │  Apply the schema's case rule.
│                        │  "My_File_NAME" → "my_file_name"
└──────────┬─────────────┘
           ▼
┌────────────────────────┐
│ 4. SPELL CORRECT       │  Simple word list (no LLM). Check each token
│                        │  against a 50K-word dictionary.
│                        │  "theophyscs" → "theophysics"
│                        │  "invioce" → "invoice"
│                        │  Only correct if confidence > 0.9 (Levenshtein 1)
└──────────┬─────────────┘
           ▼
┌────────────────────────┐
│ 5. ABBREVIATE          │  Only if schema = Smart Compact.
│    (optional)          │  "invoice" → "inv", "screenshot" → "ss"
└──────────┬─────────────┘
           ▼
┌────────────────────────┐
│ 6. DATE INSERT         │  If schema uses dates and file has a detectable
│                        │  date (from filename, EXIF, or mtime):
│                        │  Insert at the schema's date position (prefix/suffix)
│                        │  in the schema's date format.
└──────────┬─────────────┘
           ▼
┌────────────────────────┐
│ 7. LENGTH CAP          │  If stem > max_length, truncate intelligently:
│                        │  keep first word + last word + date.
│                        │  "very_long_meeting_notes_about_..." → "very_long...notes_2026_07_03"
└──────────┬─────────────┘
           ▼
┌────────────────────────┐
│ 8. COLLISION CHECK     │  Does this name already exist in the target folder?
│                        │  If yes, append _01, _02, etc.
└──────────┬─────────────┘
           ▼
STANDARDIZED FILENAME (cached in SQLite, ready instantly)

This pipeline runs in the background every time a new file appears. By the time the user clicks on it, the standardized name is already computed and waiting. The user sees instant response. The compute happened seconds ago.

Part 4: How Many GUIs Do You Need?

The answer is 4 GUIs. Not 4 apps — 4 interfaces that serve different moments in the user's workflow. Some are overlays, some are full windows, one is a tray icon.

1
THE TRAY ICON + NOTIFICATION PANEL Always running AHK or Electron

This is the system's heartbeat. A small icon in the system tray that shows status (learning / predicting / auto-pilot). Click it to see: observation count, trust level, prediction accuracy, and today's activity log ("Organized 7 files this morning").

This is NOT the AHK chat overlay. That's a separate thing for the AI relay. This is purely for the file intelligence system. Minimal UI. Just a number and a status.

When it appears: Always. Boots with Windows. Invisible until clicked.

2
THE PREDICTION OVERLAY Triggered on file action AHK floating window

This is the split-screen prediction card. It appears when the user right-clicks a file, drags it, or starts a rename. Shows: "What you're about to do" vs "What I'd recommend" with the 4 buttons (yours, mine, customize, always).

Small, dark, floating, positioned near the mouse cursor. Disappears after the user makes a choice. No full window. No settings. Just the prediction and the decision.

Size: ~500px wide × ~200px tall. Anchored to cursor position.

When it appears: On file action. Trust level 1+ only (doesn't appear during Silent Observer phase).

3
THE REVIEW DASHBOARD On demand React web app (localhost)

This is the TypingMind-inspired interface Codex is building. The full command center. Left sidebar with folder tree and source icons. Main area with the review queue: pending renames, pending moves, pending archives, duplicate resolutions. Batch approve/reject. Scan results with health grades. Prediction accuracy graphs over time. Schema switcher.

This is where the user does bulk work: "Show me everything the system wants to do to my Downloads folder" → review → approve 40 renames in one click.

Size: Full browser window. Dark theme. Runs at localhost:10000 or wherever the hub API lives.

When it appears: When the user opens it. Not always running. This is the "sit down and review" interface.

4
THE HEALTH REPORT Generated file HTML, opens in browser

This is the scan_report.py output we already built. A standalone HTML file generated after each scan. Grade circle, symptom breakdown, work order, delta comparison. The user opens it in their browser, reads it, and decides what to act on.

This is NOT a live app. It's a document. Generated, saved, shareable. The user can email it to someone: "Here's the health of our shared drive."

When it appears: After a scan. Saved as a file. Opened by the user.

What You DON'T Need

Things that seem like they'd need a GUI but don't:

• Settings page — no. The system learns preferences from behavior. The only "setting" is the naming schema selector, which is 3 buttons on the review dashboard.

• Rule editor — no. Rules are created by clicking "Always do this" on prediction cards, not by editing a config file. The review dashboard shows existing rules and lets you delete them.

• File browser — no. The user already has Windows Explorer, Total Commander, whatever they use. We augment it with the prediction overlay, we don't replace it.

• Folder structure editor — no. The scanner proposes structures. The user approves in the review queue. No drag-and-drop folder designer needed.

• AI chat for files — no. That's the AHK overlay and the Top of Mind relay. Separate product. Don't mix them.
